# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- A compaction the plugin makes itself, without Claude Code's summary, says once a session which settings files hold a `PreCompact` hook that did not run: `your PreCompact hooks did not run: …` (#126, ADR 0043). Claude Code runs `PreCompact` hooks only inside its own summary, so a hook that copies the transcript first or holds automatic compactions back stopped running once the plugin was installed, without a word. `docs/limits.md`, "Other hooks at a compaction", says what runs and what does not, measured on Claude Code 2.1.293: `PostCompact`, and `SessionStart` with the matcher `compact`, run after either; and how a plugin that hooks `session.compact` stands beside this one, the first `--plugin-dir` outermost. Another plugin's `PreCompact` hook is not named: a plugin cannot read it.
- `docs/troubleshooting.md` looks up a line the plugin prints by its own words: each line beginning `built-in compaction:` has an entry saying what happened and what to do, and the page opens with how to tell that the plugin is not running at all (#140). Each reason such a line can give is made in one place, `src/reasons.ts`, and a test holds every one of them to the page, so that a reason added without an entry fails it. `/lossless-status` ends with the page's address, as only its answer reaches the agent, and the README lists the page first. How to set the plugin up, update it and stay on a release moved from `docs/limits.md` to `docs/usage.md`, "Setting it up", as it was but for one sentence, which names the variable early access asked for no more and points at "Function hooks" for it.
- `docs/limits.md`, "Systems", says on which systems the plugin is checked and what does not work on the others, a row each for macOS, Linux, Alpine, WSL, Windows and NixOS (#147). It is checked in Claude Code on macOS only. On 2026-10-07 each command line it starts, with the arguments it gives them, was run in Docker's Debian 13, Ubuntu 24.04 and Alpine 3.24 images: on Alpine, BusyBox's `grep` refuses `--include`, so the clean-up stops each time and nothing kept is removed. The rows for WSL, Windows and NixOS are read from the code: on NixOS no `mkdir` or `chmod` can be started, so nothing is kept and each compaction is Claude Code's summary. The README's quick start names macOS and links to the section.
- The plugin's manifest names its documentation, where to ask for support and its privacy policy (`documentationUrl`, `supportUrl`, `privacyPolicyUrl`), which Claude Code's plugin directory reads (#112).
- `/lossless-store check` reads every text and entry kept, in place and in the trash, of every place results are read from, and names, once each, every id whose files are not whole, with what that does (#117): a link, or a text that no longer has the hash it is named by or does not read, which `recall` refuses; an entry with no text or a text with no entry, under which it finds nothing; an entry that does not read, whose text `recall` gives back and `/lossless-export` leaves out; an entry that gives another size, whose ticket a compaction does not take for its own; a copy in the trash that is not whole beside a whole one in place, which does nothing now. Before, a text changed on disk was found only when `recall` refused it, after its original had left the conversation, and `/lossless-store` showed an entry that does not read only as a count. A text and its entry that are whole and stand apart in place and in the trash are counted, not named, and the answer says whether `recall` puts them back; a file under a minute old is not judged; where the ten seconds a command has do not reach the end, it says where to go on from, `/lossless-store check from <place>:<id>`. Each id is named by its first 16 characters, so that the answer standing in the conversation does not keep what it names from the clean-up. One run over two places of 5,549 results took 8.8 to 10.1 s, and one over about 5,600 took 41 s on a busier machine. It shows nothing of a text and writes nothing; `PRIVACY.md` says what it reads. `/lossless-store` followed by anything but `check` now says what it takes, where it gave its usual answer.
- `find` is there with no key, and sends nothing: a quoted phrase is looked for in what was moved out on this machine and the one result that holds it comes back; the results with a line holding the values a question names are listed with that line; and a question in words lists every result by its call and first line, those written in the conversation newest first, for the agent to choose from, nothing ranked (#110, ADR 0037). Each such answer ends saying Jev was not asked. With a key, `find` is as it was. `/lossless-status` says which it is. In the benchmark the variant with no key has `find` too, and a checkout of before is measured beside it with `--without-find`.
- `/lossless-export <directory>` writes the results the conversation's tickets name, through the tickets in its kept parts, into a new directory; `/lossless-import <directory>` takes such a directory, or an earlier place, into the store, each result checked against its name, so that the conversation resumed on another machine gives them back (#116). Each runs only when typed by you, at the prompt or through Remote Control, and not on Windows. The directory written to is given from `/` with no `.` or `..`, new (or one it made, typed again to go on), outside any repository and readable by you alone; every mention in the shape of a ticket is followed, in the conversation and in what it names, and what is kept nowhere is counted. Reading in takes a result only where its text has the SHA-256 it is named by and its entry says what it is, while some of the hook's own time is left, and notes the conversation's record and a witness so that the clean-up counts what came in. Nothing is sent anywhere. Checked on Claude Code 2.1.291: written out under one `storeDir`, read in under another, and given back by `recall`.
- CI type-checks `hooks/move-out.ts` against the declarations of the Claude Code version the workflow names, and on every run checks that a copy of it whose shape of `$` is not Claude Code's fails where `$` is handed to it (#121). The hook file had never been type-checked in CI: the tests load it by a dynamic import, which the type check does not follow, and `npm run typecheck:hooks` read a file a fresh clone does not have. Claude Code writes its declarations when it loads the plugin from a folder, before it asks for a sign-in, so `npm run typecheck:hooks` (`test/typecheck-hooks.sh`) starts it once to write them where they are missing or of another version, with only `HOME` and `PATH` of your environment, a configuration directory of its own, none of your settings and its updater off, and it stops at "Not logged in"; settings an organization manages are read all the same. After `npm ci` it runs in a fresh clone. The weekly workflow runs it with the newest Claude Code.
- `/lossless-status` says that the plugin runs in this session, its version and Claude Code's, the value each number setting is used at and, where that is not what was set, what was set, whether the other settings are set, and whether `find` is registered, with where its key came from or why it is not (#108). Typed right after installing, it shows the plugin runs before any compaction has; its first lines are what a bug report needs. It is a command like `/lossless-store`, not a tool the agent is offered. It prints no key, nor the value of a field a key could have been pasted into (`provider` is shown only as one of its three values, `model` as the default or set), and reads no stored result: of the conversation it counts the tickets by their shape. Where `find` has no key, `provider` is left on `auto` with no account id and `TYPESAFE_API_KEY` is in the environment, it says that key is used once `provider` is set to `typesafe`, unless a repository's settings put it there (ADR 0028). Where what the settings give now differs from what the start of the session registered, as when a repository's settings file changed since, it says both; after a change of the plugin's own settings, which loads it again, it says what they give now. The README's quick start names it.

### Changed

- A compaction that throws while the plugin tries it says `built-in compaction: moving out failed: <what was thrown>`, where it said `built-in compaction: <what was thrown>`, so that the line has words of its own to look up (#140). The conversation is kept first and handed to Claude Code's summary, as before.
- Each setting's description in the settings dialog says, in under 250 characters, what it does, the values it takes and its default, and names the new Settings section of `docs/usage.md`, which says what to change for each aim that was measured (#142). They ran to 766 characters, eight lines at 100 columns. What the descriptions alone said, the model's window as what a share is of when automatic compaction is off, what `minChars` holds back and the model asked for by default, is in that section; the rest was in `docs/limits.md`, which it links to.
- When the provider refuses the key, `find` tells the agent what happened and what to check, with `/plugin configure`, `/lossless-status` and the address of the new Getting a key section of `docs/usage.md`, and the session tells the person once, with where to set it (#143). The answer was `Jev could not be asked: HTTP 401.`, to the agent alone. A refusal of access (HTTP 403) is told as the key, what it may reach or the account, since Cloudflare answers so for a plan or terms as well; a provider asking for payment (402) or limiting requests (429) is told the same way, and one that fails is named to the agent alone. An answer of these not in JSON, as the providers' are, from a proxy say, is put on neither the key nor the provider, and the person is told nothing of it. Every such answer ends saying `recall` still reads a result by its id. Where several requests are in flight, a refusal is kept over a failure with no status that comes after it. The README's sentence on the key links the new section, which says where TypeSafe and Cloudflare keys are made and what access a Cloudflare token needs.
- The line a compaction shows names what each of its figures counts and, in words, why anything it could not move out stayed: no code of the plugin's own reaches it (#141). It gives what was in use before as Claude Code counts it and what is in use after, in tokens with the thousands set apart, of the size at which Claude Code compacts on its own, or of the model's window where automatic compaction is off or Claude Code gave no breakdown, or of an assumed one where it gave none; the conversation in characters only where the plugin could not count it from what Claude Code gave. Results that stayed are named by why (`too large to keep (over about 4 MB)`, `could not be written (ENOSPC)`), where the line said `left in place: 1 too-large` and `could not write: ENOSPC` apart; so are the reasons the line gives where Claude Code's summary runs instead. The notice over the transcript is a short form of it, the context rounded (`~22k of 167k tokens`), and no notice repeats the plugin's name, which Claude Code draws it under: shown on one line cut at the width of the screen, the name twice took its end. Where nothing could be moved out, the line gives, where it was counted, what was in use and what the plugin counts of it less the thinking, images and what Claude Code attached, no size the conversation came to; the reasons for what attached to the messages could not be kept are worded the same way. The benchmark reads both forms, and reads a cut for the conversation's length as a cut, where it read it as results moved out; `npm run check:host` reads the line as the benchmark does. The examples of the line in `docs/usage.md` are the transcript's lines of `npm run check:host`, at the default settings but for the cut, which is at the settings it is made with, and the notice is the short form of the same report; the made-up one of 3,400 messages is written in the new form.
- A result's ticket says how many lines of text the result held: `[moved out] Bash result, 412 lines, 10605 bytes; recall with … id …` (#149, ADR 0040). A result that held images is counted by its text, and one that is an image alone is not counted. A ticket of 0.4.0 to 0.7.1, with no count, is read the same. A quote of each result's first line under its ticket was measured and is not written: with Sonnet 5.5 and no key, on seven questions of `opaque` that name a document by what it was about and ask for a line in its middle, it cut the calls to `find` and `recall` from 13 to 15 a run to 4 to 7, and the right answers from 6 or 7 to 4 or 5, the agent giving a ticket's id as the code asked for without reading the result (`docs/measurements.md`). `find`'s list with no key chooses each result's first line as the first with a letter or a digit, so a `{` or a rule is passed over, takes `Read`'s number off where Claude Code added a line after the reading, and does not show a line holding an id, the plugin's name, `[moved out]` or the words an answer of `find` opens with. The benchmark records, for each question, the bytes `recall` and `find` handed back and the ids handed to `recall` that held nothing asked for, and `opaque` has seven questions that name a document by what it was about and ask for a line in its middle.
- With a key, `find` blanks more before it sends (#131): payment keys written `sk_live_`, `sk_test_`, `rk_…`; npm, PyPI and RubyGems tokens; values given in an environment file or a shell to a name in capitals ending in `_KEY`, `_PASS`, `_PW`, `DSN`, `_WEBHOOK` or `_WEBHOOK_URL`, or named `DSN`, and secrets whose quote is escaped as JSON escapes one; the password of a URL with no user, and the user of a URL with no password (as a DSN holds a key); the paths of Slack, Microsoft Teams and Discord incoming webhooks; email addresses; and telephone numbers written with `+`, a country code and groups (8 to 15 digits), and `tel:` links. PRIVACY.md lists every shape. A kept part's call line is blanked again as it is sent, whichever version kept it, and the call lines written into kept parts and the lines an answer shows are blanked the same way. With no key, the values a question names are taken from it as asked, since nothing is sent: a telephone number in it is still looked for.
- The Settings section of docs/usage.md says that `minChars` also bounds the old calls that fold into a list, so that raising it folds more of them, and that `targetPercent` and `keepTokens` keep more in the context; the setting's title says "one by one" (#120). What the plugin does is as before.
- `recall` and `find` read every place results were written to under your settings since this version, and the default places when `storeDir` is set, the current one first: a ticket written before `storeDir` was set or changed comes back, where it was refused as not stored (#116, ADR 0035). The places are noted, up to 16, in the plugin's own store under `~/.claude/plugins/store/`; one not found stays on the list. Only the place of the settings in use is cleaned up, made private and put back into from the trash: an earlier one is read alone, since another configuration may still use it. `/lossless-store` counts the earlier places after the current one. The defaults are read beside a `storeDir` only where the repository's settings did not set `HOME`, `USERPROFILE` or `CLAUDE_CONFIG_DIR`. Places written to before this version are noted once used again. `PRIVACY.md` names the list.
- The marketplace entry names no version: `plugin.json` alone holds it, as Claude Code reads it first (ADR 0031). `npm run validate` checks the marketplace with `--strict` too, which a description of it now lets pass. docs/usage.md says how to update an installed copy, which version it is, and how to stay on a release: added at its tag; going back removes the plugin's settings, `storeDir` among them. docs/development.md, "Releasing", sets out how a release points the marketplace at its tag rather than the tip of `main` (#106); until one does, it points at `main`.
- A conversation near the 4096 entries Claude Code hands a plugin is cut for its length (#115, ADR 0034). At a compaction without instructions, one handed over with 1,536 entries or more is cut down to 1,024 messages, its oldest kept in parts with no summary and the first message in front, however much room is left: where moving results out was enough, and at a `/compact` by hand that had nothing to move out. Before, no summary started the count over under the plugin, and a conversation that reached 4096 was summarized with what was older than the 4096 not kept. Counted on one machine (`docs/measurements.md`), a conversation gathered 1,510 entries at the median and 2,045 at most between an empty start and the next compaction, which is as much as one compaction can add at `targetPercent` 1, where what is in use goes down to little and the messages stay; none counted reached 4096 yet, the most being 2,081. With instructions the summary that was asked for runs, as before; where no place to cut is left or a part cannot be written, the compaction goes as it would have. The line says the conversation was cut for its length and names the entries, and `/lossless-status` says how many of the 4096 the conversation holds. `bench/messages.ts` counts them from your own records, numbers only.
- A `/compact` given instructions, typed or asked for by a plugin, moves out what it can, then hands what is left to Claude Code's summary with them, though moving out made room: it was handed back rebuilt then, and the instructions only ordered what left first, which at `targetPercent` 1 left them nothing to do (#111, ADR 0036). The conversation is kept first; where the disk refuses that write, nothing runs (ADR 0008). To have a summary, give `/compact` any instructions. An automatic compaction goes on as before, even where another hook hands it instructions.
- `recall` takes an id the agent copied wrong for the one id written in the conversation that shares the most characters with it from the first, 8 or more, where no other shares as many (#107); it was the one that begins with its first 16 characters. In one session that compacts several times (`docs/measurements.md`), Sonnet 5.5 was refused 8 times in three runs of 0.7.0, and two answers were lost to it: each time it dropped one of a pair of characters written twice over, `406e6e8` copied as `406e8`, ten characters in, and handed the id cut short at 11 characters, those 11 twice over, at 62, or made up past the tenth. 7 of the 8 are taken now. Driven again at 1 and at 40, three runs each, on this code (`bench/results/2026-10-06-session-ids/`), the same 62 characters were handed twice in 33 calls to `recall`, and taken both times, the question answered right; none was refused, and every question of the six runs was answered right. An id written in the conversation that is the one handed, whole, as Claude Code's summary can hold one the agent copied wrong, is passed over for the one it was copied from, where before the two made it refuse. A refusal of what may be an id copied wrong now names up to five tickets of the conversation it may stand for, each with what it stands for where the conversation says and its id: those whose ids begin as it does, the most characters first, then the parts kept from the conversation, newest first, whose own tickets are not written in it, as for the eighth, copied from the summary while its ticket was only in a part (whether that part was among the five was not measured). Where the id handed is itself written in the conversation, it says nothing is stored under it here and names the parts alone, so that no other result is read in its place. A copy written whole and handed twice over is read past to the one it was copied from as well. The benchmark records each call to `recall` of a session, the id handed and whether it was refused, and `session-report` tables them for the runs that recorded them.
- A key in the environment (`TYPESAFE_API_KEY`, `CLOUDFLARE_API_TOKEN`) is used only where the plugin's own settings choose the provider: `provider` set to `typesafe` or `cloudflare`, or a Cloudflare account id entered (#103, ADR 0028). Left on `auto` with no account id, as the settings are untouched, only a key set in the plugin's settings is used, so a `TYPESAFE_API_KEY` exported for another tool no longer registers `find` and sends excerpts at its first call. If that key is how you set `find` up, set `provider` to `typesafe` with `/plugin configure lossless-compaction@lossless-compaction` to have it again; nothing says so at the start of a session, and `/lossless-status` says it.
- The README compares the plugin with the built-in compaction at `targetPercent` 1, the default, where its figures were of 40 (#109). The plugin's arm was measured again with Sonnet 5.5, beside the built-in compaction's run of 2026-10-04 on the same six conversations and Claude Code 2.1.289, a `/compact` by hand then nine questions one after another, twice: the plugin's `/compact` took 0.11 to 0.48 s against 15 to 27 s; the next request carried 7,970 to 18,243 tokens against 9,044 to 30,735, smaller in five kinds of six; 102 answers of 108 were right against 96; and in the first run the `/compact`s with their questions cost 0.65 USD against 2.17. In a window of 1,000,000, the eleven questions were all right against 6, at 0.14 USD against 1.58. The figures at 40 stay in `docs/measurements.md` and `docs/comparison.md`.
- A subagent's compaction keeps its conversation before Claude Code summarizes it, and the ticket of what was kept stands after the summary, as for the main conversation (#101, ADR 0026). Before, a subagent's conversation went to the summary with nothing kept and nothing said, where `docs/invariants.md` says each compaction says so. Nothing of a subagent's conversation is moved out or rebuilt, as before. Its line goes to the transcript alone, starting `subagent <its id>:`, with no notice. Where the disk refuses the write, its summary runs all the same, with nothing kept: no one can compact a subagent again once room is made. `recall` in a subagent takes an id copied wrong for the one its own conversation names; `find` still does not look there, and says where what was replaced went.

### Fixed

- A project directory of transcripts that grew past what one search reads in five minutes, or whose ids passed the 4 MiB Claude Code keeps of what a command prints, stopped every clean-up from then on, daily. Its transcripts are now read a set at a time, at most 400 files and 256 MiB a search; a search cut short is read again in halves, and a transcript removed while a clean-up reads, alone or with its session's directory, is passed over. Only one transcript alone too large to read in five minutes, or with more ids than a command may print, stops it (#118, ADR 0042). Nothing of what was read is kept between clean-ups: each reads every transcript, as before.
- A search of the transcripts that did not end in its five minutes was run again with the other `grep`, where both are there (a Linux whose `/bin` is `/usr/bin`), doubling the time a clean-up then spent before it stopped; a transcript a witness is looked for in likewise. The `grep` is now chosen once, by a small search of a file of the plugin's own, and a search with it that does not come back stops the clean-up (#118).
- Clean-ups that run at once, as sessions started together can start, could remove the only text of a result one of them names, and `recall` then answered that nothing is stored (#119, ADR 0038). One clean-up moved the result to the trash, entry first and text after; another, which names it, put back what the trash held and, finding the text still in place, removed what the trash held of it as a copy, by then the text itself. A copy the trash holds of a result in place is now removed only from a day two or more days past, which no clean-up is still moving into; a newer copy stays a little longer. Storing a text already stored now renews its file's time with `touch`, so a clean-up within a day of the new use no longer moves it to the trash before a transcript names it; where no command can be started, as on Windows, the day is counted from the first time, as before. `PRIVACY.md` names `touch`.
- A place transcripts are kept in that is itself a link, `~/.claude/projects` linked to another disk say, no longer stops every clean-up: each clean-up reads it where it leads then, so a link turned to another place is followed (#119, ADR 0039). A store kept beside such a place was never cleaned up, from the first clean-up on. One recorded both under the link and where it leads is read once; where Claude Code cannot tell where it leads, the clean-up stops. And a trash that is there and cannot be listed now stops a clean-up before anything moves, where it was read as empty, and `/lossless-store` says it could not be listed rather than that it is empty (#119).
- A file a write left in `tmp/` when its process stopped partway, up to 4 MiB each, no longer stays until removed by hand: the first clean-up that runs to its end once it is a day old removes it, by its name a write's own (#119). `/lossless-store` tells those from other files left in `tmp/`, which stay until removed by hand. How long one `sync` took to return after a compaction's writes is in `docs/measurements.md`, about 50 ms here; the plugin still does not ask the disk to keep what it writes, and `docs/invariants.md` says so as it is.
- A stored thing whose entry, `index/<id>.json`, does not read no longer stops every clean-up where its text is there and is the one stored: the text is read as a kept part's, and what it names is kept and put back from the trash (#114, ADR 0033). A text that is not there, does not read or has changed still stops it.
- A clean-up stopped by a kept part that cannot be read, or by something named that could not be put back from the trash, now finds every such one it reaches in that try, records their ids and why in `gc.json` (twenty, and how many more), and `/lossless-store` names each with how the clean-up goes on; it said only that one could not be read, and found the next a day later (#114). An entry that does not read back after it is written is no longer taken for one placed: the result stays in the conversation, where a ticket would have named something `recall` cannot find. An entry of another shape than every version writes is no longer read as saying the thing is not a part.
- A store used from two machines, through a synced folder, a network drive or the same `storeDir`, is no longer cleaned up from one of them, which removed what only the other's conversations named (#113, ADR 0032). Each session marks the store in `machines/`, under its machine's id (made once in `~/.local/state/lossless-compaction/machine.json`) or, with none, its own, with the machine's latest sessions; a clean-up that finds a mark none of whose sessions has a transcript it can read stops before anything moves, and `/lossless-store` lists the marks and how to go on. A container made again over the same transcripts goes on, and its earlier mark is taken off at the clean-up while their transcripts last. A machine that runs an earlier version leaves no mark.
- A number setting outside its range is taken at the nearest end of it, where it was replaced by its default without a word (#99). `targetPercent` set to 100 was used as 1, which since 0.7.1 is the other end of what was asked for: everything that may leave moved out at every compaction. That is said once, at the start of the session, as is a value left empty, which is taken at its default; each number setting's description names its range. A value that is not a number keeps Claude Code from loading the plugin, as before.
- A clean-up could take every result of a conversation for unused, and remove it two weeks later with nothing said, were Claude Code to write its transcripts otherwise than its search reads them: compressed, renamed, with ids spelled another way, or inside the directory it keeps beside each (#100, ADR 0027). At each compaction of the main conversation, and when a session starts with tickets, the conversation's newest ticket is noted in `witness/`. Before anything moves, a clean-up looks for each in its conversation's own transcript: not there, or the conversation still there under its session id in another form, it stops, and says so. A noted ticket whose conversation is gone lets go. Conversations compacted before this version have none until resumed or compacted again. `PRIVACY.md` names the new file and what is read.
- A compaction whose hook throws, answers what Claude Code refuses, or outruns its time no longer leaves Claude Code's summary to run with nothing kept and nothing said (#102). Claude Code takes such a hook for absent; the hook now has a handler of a failure, which says what failed, keeps the conversation as it was sent and hands it to the summary, with the tickets of what was kept after it, as where the compaction could not be tried. Where the hook had already asked for the summary, it is not asked for again, and the tickets follow what it came to. Where Claude Code went on without the hook while it was trying the compaction, the hook says and hands on nothing more once the try is over. The handler has a second of its own time, waits on the disk not counted: keeping 4,096 messages of six million characters took 59 ms, in memory, where it was measured. `npm run check:host` breaks copies of the plugin four ways (`test/fixtures/failing/`) and checks each on the Claude Code you have; `claude plugin validate --strict` of 2.1.287, 2.1.288 and 2.1.291 accepts the hook file.
- A line of a tool's output, of what was said or of an input that reads as one of a kept part's fixed lines (`--- user`, `--- assistant`, `[call …]`, `[result …]`) no longer reads as one once the part is recalled (#104, ADR 0029). A fetched page holding `--- user` came back looking like something the person had said, `find` named the middle of a message of Claude's after such a line as the person's, and the lines of a result after a `[call …]` of its own were put under that call. Such a line is now written with a backslash in front, and so is one a model would take for a fixed line, ending in a space or a carriage return or led by spaces; taking one backslash off gives the text back as it was. A line longer than a part is cut one character earlier where what follows would start as a fixed line. `recall`'s description says how a part is read. Parts written before are read as they were and are not written again.
- What Claude Code attached to the messages as it sent them — a file handed over with `@`, what a hook added to what was said or to what a tool returned, the text it shows with a command, reminders — is no longer lost when the plugin rebuilds the conversation (#105, ADR 0030). None of it is in the messages a compaction hook is handed: on Claude Code 2.1.291 the agent, asked after a compaction for a word of a file it had been handed with `@`, answered that it was not visible. At each compaction that rebuilds the conversation, cuts it or hands it to the summary, what the conversation as sent holds beyond the messages is now kept in parts, each block under a heading naming the message it came with and one sent again written once, and a message at the end of what is handed back (of the conversation kept before a summary, where one runs) names them, so that what an earlier compaction left stays as it was. Where those parts cannot be written, the conversation is not rebuilt but kept as sent before the built-in summary, or, refused that too, left as it is. `find` looks through them here and sends nothing of them to Jev; PRIVACY.md lists what they hold.

## [0.7.1] - 2026-10-05

### Added

- The benchmark tells a failure to fetch an answer from a failure after fetching it (#90). For each question whose answer no file holds any more, a unit of the plugin's arm that asks its questions one at a time records whether the answer still stood in the conversation, whether something moved out holds it, whether the agent called `recall` or `find`, whether it chose a piece that holds the answer, and whether what came back held it; `report` tables them. Measured with Sonnet 5.5 and no key for Jev (`bench/results/2026-10-05-fetched/`): 81 of 84 answers that had to be fetched were, where the oldest messages were cut once the results had left as where results alone left, and the three that were not are one question a run that another model answered after Sonnet 5.5 refused. `bench/main.ts find --variants default` measures `recall` alone without a key.
- `docs/invariants.md` says what "lossless" holds to, in eight promises, and what is not promised (#90): a ticket stands only for what was written, read back and found equal, a result, a long input, a long message and a run of folded calls alike; `recall` returns what was stored or nothing; what is stored is not written over; the clean-up removes nothing a conversation can still reach, and moves nothing when it cannot tell; what a cut takes out is kept first, and a summary does not run on a refused write; what went to the trash in use comes back; a conversation holding what a rebuilt message cannot carry is not rebuilt. Each promise names the tests that keep it, and `npm run mutate` breaks 31 lines of `src/` that the promises rest on, one at a time, and checks that the test named for each fails.
- The benchmark drives one session through several compactions under each of five settings: Claude Code's own compaction, the plugin with `targetPercent` at 40, 20 and 1, and the plugin moving results out before Claude Code summarizes what is left (#53, #90; `bench/main.ts session`, `bench/results/2026-10-05-session/`). With Sonnet 5.5 in a window of 200,000, two runs each: at 40 the session compacted five times and cost 5.02 and 5.13 USD, at 20 and at 1 four times (three in one run) for 4.03 to 4.23, the built-in three times for 3.85 and 4.03 with three of its five right answers read from Claude Code's own record of the session, and moving out before a summary left least in use and answered every question for 4.25 and 4.38. `docs/measurements.md` has the table: the compactions, what was in use before and after each, what the request after each read from the prompt cache and wrote to it, the cost at three points, the time and the answers.
- `PRIVACY.md` says what the plugin reads, keeps and where, sends and to whom, which programs it runs, how long it keeps what it kept and how to remove it (#89). The plugin itself sends nothing without a key for Jev, and nothing ever to the maintainer; with a key, `find` sends the provider what `docs/usage.md` lists. `test/privacy.test.ts` reads the code for the addresses, the programs and the places written in it, and fails when the page does not name one, or when the code sends another way than the one call `find` uses; it does not see one that the code puts together some other way. The README links to it.

### Changed

- `targetPercent` is 1 by default, where it was 40 (#53, ADR 0025): a compaction moves out everything that may leave, but the newest `keepTokens` of results, of long inputs and of long messages, and the calls among the newest `keepTokens` of the conversation, and a cut in place of a summary goes as far. In one session driven through several compactions with Sonnet 5.5 in a window of 200,000, at 40 about 65,000 tokens stayed after each compaction, left at the next, and were written to the prompt cache again each time: five compactions and 5.02 and 5.13 USD, where at 1 three or four and 4.03 and 4.23, with as many answers right. A rule fixed before the session was driven decided it, and `bench/session.ts` holds it (`defaultFrom`). On the six conversations of the benchmark, a `/compact` by hand at 1 left the next request at 7,373 to 17,641 tokens against 10,766 to 83,460 at 40, with 52 answers right of 54 against 53. More is behind tickets afterwards, at automatic compactions as well: there long inputs and the middles of long messages older than the newest `keepTokens` of their kind leave every time, where at 40 they left only when results were not enough. In a window of 1,000,000 the target is 9,670 tokens, reached only where what is left comes to less. A value you set stays as you set it; set 40 to have the old behaviour. `docs/limits.md` says what each end costs.
- `bench/replay.ts` takes from the record the window and whether the compaction was typed. A session that sent more than 200,000 tokens in any request is replayed in a window of 1,000,000, where the window was taken from the size at the line replayed, so a `/compact` typed early in such a session was replayed in the wrong one. A compaction the record says was asked for is replayed as a `/compact` typed without instructions, which reaches into the newest calls, where every compaction was replayed as one Claude Code started (`--with-instructions` for one that had them). The window can be given; the target is 1 unless given; and it prints the target, the size it is a share of, and how many results, inputs, middles and calls left. With it, `docs/measurements.md` gives the first compaction of eight working sessions in a window of 1,000,000 replayed at 1, 20 and 40: the same at each in seven, and at 40 3 % more left in one typed.
- What the store keeps and gives back is in files that know nothing of Claude Code (#90): `src/blobs.ts` stores a text under the SHA-256 of itself and reads it back, with `src/layout.ts`, `src/files.ts` and `src/encoded.ts` (how a result with images is held as text, taken out of `src/media.ts`); the tickets, which name the tool the model calls, and where a store is under Claude Code's directory stay in `src/store.ts`. `test/layers.test.ts` holds that those four files carry no tool name, directory or variable of Claude Code's, no shape of a conversation and nothing of a hook's `$`, and read no file outside themselves; `docs/development.md` says which layer a file is of. What decides what leaves a conversation still reads a conversation as Claude Code hands it over. Nothing the plugin does changes, and no test of it changed.

### Fixed

- A result named only in a kept part is no longer removed when that part was in the trash and is named again. A part whose entry is in the trash was not known for a part, so the clean-up that put it back did not count what it names, and removed it if the trash had held it over a week: the part then came back with tickets for results that were gone. That took a part going to the trash while still wanted, as when the disk its transcript is on is not mounted at a clean-up. What the transcripts name now goes back from the trash, with what the parts among it name, before the clean-up counts what is named; and a clean-up stops, moving nothing to the trash and removing nothing, where something named, by a transcript or by a part, is in the trash and not in its place.

- The ticket left in a result's place is shorter: `[moved out] <tool> result, <bytes> bytes; recall with mcp__jev-lossless-compaction__recall id <id>`, 154 characters for a `Read` where the old wording took 258. Tickets in the old wording are still recognised. A result of the `recall` tool itself is named `recall` in its ticket.

## [0.1.0] - 2026-09-30

### Added

- The plugin. On a compaction, old tool results are written to local files, read back and compared, and replaced in the conversation by a one-line ticket. The tool calls themselves stay.
- A `recall` tool that returns a moved-out result unchanged, after checking it against the SHA-256 it is stored under.
- Ordering by Jev: one `score` question per tool result, with a digest of the result in the question. TypeSafe and Cloudflare Workers AI are supported as providers. Without a key nothing is sent and rules decide the order.
- Fallbacks: rules decide the order when Jev fails or takes longer than five seconds; Claude Code's built-in compaction runs when the conversation holds an image, a document or a block of a kind the plugin does not know, has 4096 messages or more, belongs to a subagent, has nothing that can be moved out, or is still too full afterwards and a summary could change that.
